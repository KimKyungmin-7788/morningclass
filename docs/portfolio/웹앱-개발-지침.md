# 아침교실 연동 교육 웹앱 개발 지침

> 운영 방향 변경(2026-10-24): 공개 버전은 로컬 전용이다. 클라우드 규약은 제작자의 서울 프로젝트 개인 운영 또는 각 개발자의 독립 자가 운영에 적용한다. 허브 계정 공유·공개 회원 모집은 하지 않는다. [현재 운영 설계](./계정과-서비스별-가입-설계.md)를 우선 읽는다.

상태: **설계 초안 0.1 · 공통 연결 모듈 미구현**  
작성일: 2026-10-24

새 교육 웹앱을 만들거나 기존 앱에 결과 전송을 추가할 때 사용하는 개발자·코딩 에이전트용 지침이다. [공통 연동 규약](./공통-연동-규약.md)이 자료 형식과 전달 계약의 기준이다. 이 문서만 복사하지 말고 규약과 [후속 협의](./후속-협의.md)를 함께 제공한다. 이 지침은 앱의 수업 화면이나 QR 사용을 강제하지 않는다.

## 1. 먼저 확인할 것

프로젝트의 AGENTS.md와 저장소 규칙을 읽고, 공통 규약·실제 서버 명세·SDK가 존재하는지 확인한다. 현재 초안과 실제 구현이 다르면 차이를 문서화하고 사용자에게 확인한다. 아직 서버가 없다면 가상 수신 어댑터를 만들고 운영 전송은 비활성화한다.

다음 표를 앱의 `docs/아침교실-연동.md`에 작성한다.

| 항목 | 개발자가 정리할 내용 |
|---|---|
| 활동 | 앱 ID, 활동 ID·버전, 학습 목표, 교과 |
| 결과 | 활동의 완료/중단 기준, 결과 요약, 완성 작품 유무 |
| 지표 | 측정 가능한 항목, 정의·단위·산출식·분모·관찰 주체 |
| 비교 | 난이도, 과제 세트, 도움 조건, 첫/재시도 등 필수 비교 조건 |
| 학생 연결 | 선택한 접속 UX, 학생 배정 확인, 공유 기기의 학생 전환 |
| 전송 | 실제 또는 가상 어댑터, 실패·오프라인·재연결 화면 |
| 미정 | 서버·인증·자료 정책처럼 사용자 결정이 필요한 항목 |

**완료 기준:** 측정하지 않는 값을 0으로 만들지 않고, 기록할 값과 비교 조건을 모두 설명할 수 있다. 정해지지 않은 학습 평가 기준은 사용자에게 묻는다.

## 2. 활동 모델과 전송 코드를 분리한다

프로젝트 구조에 맞게 아래 책임을 별도 모듈로 둔다. 프레임워크·폴더명 자체는 자유다.

- 활동 모델: 학생 입력을 받아 완료 결과를 계산하는 순수 함수
- 결과 변환: 활동 결과를 규약의 봉투로 바꾸는 함수
- 학생 연결: 서버가 검증한 연결 상태와 만료/해제 처리
- 전송 어댑터: 인증된 제출·상태 확인·첨부 업로드
- 대기열: 원래 소유 학생·resultId·첨부·재시도 상태 보관
- 화면: 활동 진행과 전송 상태 표시

실제 공통 SDK가 제공되면 그 공개 API를 사용한다. 제공되지 않았다면 아래와 같은 **개념적 인터페이스**를 앱 내부에 두되, 존재하지 않는 패키지나 서버 주소를 만들어 사용하지 않는다.

```ts
// 개념 예시. ResultEnvelope/Receipt/연결 자료형은 확정 규약에서 가져온다.
interface PortfolioTransport<ResultEnvelope, Receipt> {
  submit(result: ResultEnvelope): Promise<Receipt>;
  getReceipt(resultId: string): Promise<Receipt | null>;
}
```

가상 어댑터는 성공·오프라인·시간 초과·인증 만료·중복·충돌을 재현할 수 있게 한다. 운영 빌드에서 가상 성공을 실제 저장 완료로 보여주지 않는다.

**완료 기준:** 전송 서버를 바꿔도 활동 계산을 다시 작성하지 않는다. 연결 정보가 없어도 앱이 정한 독립 실행 방식으로 활동할 수 있으며, 결과를 임의 학생에게 보내지 않는다.

## 3. 연결 UX를 선택하고 학생 혼동을 막는다

QR, 링크, 교사 지정 등 앱에 적합한 진입 방식을 선택한다. 실제 인증·학생 배정 검증은 규약 3장을 따른다. 화면에는 교사가 확인한 학생 표시명 또는 별칭과 전송 대상을 최소한으로 보여준다.

공유 태블릿에서 학생을 바꿀 때 이전 활동 초안과 새 활동을 분리한다. 이전 학생의 미전송 자료가 남아 있으면 그 학생에게 귀속된 대기 상태로 유지한다. 인증이 만료되면 같은 학생 연결을 회복해야 전송할 수 있다. 학생 이름 목록을 공개하거나 이름 입력만으로 제출 대상을 확정하지 않는다.

**완료 기준:** 학생 A 활동 완료 후 학생 B로 바꿔도 A 결과가 B에게 저장되지 않는다. 학생은 다른 학생의 결과를 조회할 수 없다.

### 학생별 QR을 사용하는 기본 구현 흐름

- 교사용 아침교실에서 학생별 QR 발급 → 태블릿에서 접속 코드 교환 → 서버가 확인한 학생 표시 → 활동 완료 → 수신증 확인 → 해당 학생 포트폴리오 수신 순서로 구현한다.
- 이름은 표시용이며 매칭 키는 `learnerId`다. 제출 시에는 인증된 `bindingId`를 보내고 서버가 학생을 결정한다. 이름 검색으로 자동 연결하거나 임의 학생 ID를 신뢰하지 않는다.
- QR에는 원시 학생 정보 없이 짧게 유효한 일회용 교환 코드만 넣는다. 연결 교환·만료·철회는 서버가 검증한다. 화면상 QR 그림이나 로컬 성공 상태를 실제 인증으로 취급하지 않는다.
- 동명이인 구분 번호·별칭을 함께 보여주되 학생에게 전체 명단이나 다른 학생 결과를 공개하지 않는다. 기존 외부 앱 학생과의 연결은 교사가 확인한다.
- 공용 태블릿에서는 학생 변경 시 활동 초안을 분리한다. 이전 결과의 binding을 새 학생 것으로 덮어쓰지 않는다.
- 서버가 없는 시안은 가상 동명이인 2명으로 학생별 결과 분리를 체험하게 한다. 실제 QR 발급·카메라 접속·권한 검사·영속 저장은 미구현임을 표시한다.

## 4. 결과를 완료 시점에 만든다

학습상 의미 있는 완료/중단 시점에 결과를 고정한다. sessionId와 resultId를 생성하고 먼저 기기 내 대기열에 저장한 뒤 제출한다. 첫 시도·재시도·정답·도움 사용을 관찰 가능한 범위에서 구분한다. 단순 페이지 체류 시간을 집중도나 학습 능력으로 바꾸지 않는다.

예시 자료는 실제 학생 자료와 별도의 시험 환경·저장소를 사용한다. 예시 결과가 운영 수신 서버로 전송되지 않게 한다. 앱에 없는 정보를 전송 형식을 채우기 위해 추정하지 않는다.

**완료 기준:** 활동 모델의 같은 입력은 같은 의미의 결과를 만들고, 전송 재시도는 새로운 학습 기록을 만들지 않는다.

## 5. 결과물·전송 상태를 연결한다

규약 6~7장의 첨부·수신증·재전송 규칙을 구현한다. 성공은 영속 저장 수신증으로 판정한다. 보내는 중 창을 닫아도 원래 ID의 대기 결과를 복구한다. 제출 오류에서 원본 결과가 유실되지 않게 한다.

앱은 간결한 완료 화면을 제공한다. ‘활동을 마쳤어요’와 ‘아침교실에 저장했어요’는 서로 다른 상태다. 전송 실패 후에도 학생이 활동에 실패한 것으로 표현하지 않는다. 학생 기기에 다른 학생 결과를 보여주는 포트폴리오 링크를 만들지 않는다.

**완료 기준:** 오프라인 완료 → 새로고침 → 연결 회복 → 한 번만 저장되는 흐름을 확인한다. 제한 용량 초과·잘못된 첨부·만료된 연결은 해결 가능한 안내로 끝난다.

## 6. 아침교실 수신부를 구현하는 경우

규약 8장의 날짜별·활동별·비교 규칙을 따른다. 서버에서 검증된 학생 소유 범위로 조회를 제한한다. 앱 등록 정보와 결과 원본에서 표시 자료를 만들며, 원본과 분석 결과를 분리한다.

같은 앱의 활동이라도 비교 필수 조건이 다르면 변화 그래프에서 제외하거나 별도 묶음으로 표시한다. 제외한 기록의 존재와 사유를 교사가 확인할 수 있게 한다. 누락은 0이 아니다. 서로 다른 교과 점수를 총점으로 합산하지 않는다.

종합의견 생성에 들어가기 전에 [후속 협의](./후속-협의.md)를 읽고 사용자에게 공동 검토를 요청한다. 현재 시안의 고정 초안을 실제 프롬프트로 채택하지 않는다. 실제 학생 데이터를 모델 제공자에게 보내는 범위도 별도로 확정한다.

**완료 기준:** 모든 비교·의견에서 어떤 원본 기록과 조건을 사용했는지 추적할 수 있다. 정정된 결과가 이전 결과와 중복 집계되지 않는다.

## 7. 필수 검증 시나리오

단위 시험은 계산·변환·검증을, 통합 시험은 저장과 권한·전송 계약을, 실제 기기 시험은 터치·기기 전환·네트워크 복구를 확인한다. 시험할 실제 사용자 자료는 먼저 백업하고 복원한다.

| 시험 | 기대 결과 |
|---|---|
| 정답 개수 0 / 미측정 | 0은 측정값, 미측정은 값 없이 구분 |
| 분모 0·범위 밖 값·미지원 버전 | 명확한 검증 오류 |
| 완료·중단·첫 시도·재시도 | 의미가 섞이지 않은 결과 |
| 동일 ID·동일 내용 두 번 제출 | 기록 한 건, 동일 수신증 |
| 동일 ID·다른 내용 제출 | 충돌 오류, 원본 유지 |
| 저장 직후 응답 유실 | 재전송해도 한 건 |
| 오프라인·새로고침·재연결 | 대기 결과 유지·복구 |
| 연결 만료·학생 교체 | 원래 소유자 확인 전 전송 보류 |
| 같은 이름의 학생 두 명 · 서로 다른 교사 | ID와 소유 범위별로 결과 분리 |
| 학생 이름 변경 | 기존 ID와 과거 결과 유지 |
| QR 만료·재사용·철회 | 접속 거부, 재발급 안내 |
| QR로 A 활동 후 B로 전환 | A의 대기 결과는 A에게만 저장 |
| 학생 A가 B의 binding·첨부 참조 사용 | 서버에서 거부 |
| 학생 세션으로 교사 조회·다른 학급 조회 | 서버에서 거부 |
| 첨부 중단·용량 초과·위장 MIME | 부분 자료를 정상 결과로 취급하지 않음 |
| UTC 날짜 경계·늦게 도착한 결과 | 수행 시간대의 원래 날짜로 표시 |
| 비교 조건 누락·난이도 변경 | 비교 제외와 이유 표시 |
| 단일 기록·작품만 있는 활동 | 변화 단정·임의 점수화 없음 |
| 결과 정정·삭제 | 기존 분석·첨부·집계 영향 처리 |
| 모바일 터치·공유 태블릿 | 작은 화면에서도 대상과 전송 상태 식별 |

자동 시험으로 확인할 수 없는 사항은 실제 기기에서 확인하고 ‘미확인’으로 보고한다. 미확인 항목을 통과로 쓰지 않는다.

## 8. 납품과 운영 전환

개발 완료 보고에는 다음을 포함한다.

1. 앱·활동 정의와 가상 결과 예시, 지원 규약 버전
2. 연결 모듈 사용법과 필요한 환경 설정 이름(비밀값 제외)
3. 구현된 저장·전송·조회 범위와 실제/가상 연동 구분
4. 시험 결과, 직접 확인한 기기·브라우저, 미확인 항목
5. 자료 보관·삭제·권한 처리, 남은 사용자 결정 사항
6. 외부 전송 도입에 따른 개인정보 안내·CSP 등 관련 설정 변경

운영 연결은 규약의 미정 항목을 확정하고 실서비스 권한 시험을 통과한 뒤 진행한다. 커밋·배포는 해당 프로젝트의 사용자 승인 범위를 따른다.

## 새 웹앱 개발 요청에 붙일 문구

> 이 교육 웹앱은 아침교실 포트폴리오와 연동할 예정이다. 첨부한 ‘공통 연동 규약’과 ‘웹앱 개발 지침’을 먼저 읽고, 앱·활동 정의와 결과 형식을 문서화해 줘. 접속 UX는 활동에 맞게 설계하되 학생 연결과 결과 전달 계약을 준수해 줘. 서버나 SDK가 아직 없다면 가상 어댑터로 구현하고, 실제 학생 자료를 전송하거나 가상 저장을 실제 저장이라고 표시하지 마. 계산·결과 변환·전송을 분리하고 지침의 검증 시나리오를 확인해 줘. 미정 평가 기준과 운영 정책은 나에게 물어봐.

## 무료 시험 운영의 첨부 제한

첫 시험의 압축·용량·한도 초과 처리는 [무료 시험 운영·용량 설계](./무료-시험운영-용량-설계.md)를 따른다. 초기 기본값은 이미지 목표 200KB, 최종 상한 500KB, 학급별 누적 파일 100MB다. 서버가 학급·전체 예산을 원자적으로 예약하고 실제 크기를 검증한다. 용량 초과는 저장 성공이 아니며 필수 작품을 누락한 채 완료 처리하지 않는다. 대기 결과는 원래 학생 연결을 유지한다. 첫 시험은 이미지·텍스트만 지원한다. 아직 운영에 적용하지 않았다.
